# 타지살이 개발 공통 규칙

타지살이 프로젝트에서 함께 지켜야 할 개발 공통 규칙입니다.

Frontend와 Backend Repository에 공통으로 적용하며,
기술별 상세 작성 기준은 각 Repository의 코드 컨벤션을 따릅니다.

---

## 1. 브랜치 전략

타지살이 프로젝트는 `main`, `dev`, `feat/*` 브랜치를 사용합니다.

```text
main
└── dev
    ├── feat/settlement-plan
    ├── feat/property-input
    ├── feat/property-analysis
    └── feat/expense-summary
```

### `main`

배포 가능한 가장 안정적인 코드를 관리합니다.

* 배포 가능한 코드만 유지합니다.
* `dev`에서 통합 테스트를 마친 후 병합합니다.
* 직접 Push하지 않고 Pull Request를 통해 병합합니다.

### `dev`

개발한 기능을 모아 통합하고 테스트하는 중간 브랜치입니다.

* 각 `feat/*` 브랜치를 병합해 기능이 함께 정상 동작하는지 확인합니다.
* 직접 Push하지 않고 Pull Request를 통해 병합합니다.
* 새로운 작업 브랜치는 최신 `dev`에서 생성합니다.

### `feat/*`

기능 하나를 짧게 작업하고 병합 후 삭제하는 브랜치입니다.

* 반드시 `dev` 브랜치에서 생성합니다.
* 하나의 브랜치에서는 하나의 기능 또는 작업만 진행합니다.
* 작업 완료 후 `dev`를 대상으로 Pull Request를 생성합니다.
* 병합이 완료된 브랜치는 삭제합니다.

---

## 2. 브랜치 생성 방법

작업을 시작하기 전에 로컬 `dev` 브랜치를 최신 상태로 갱신합니다.

```bash
git switch dev
git pull origin dev
git switch -c feat/기능이름
```

예시:

```bash
git switch -c feat/login
git switch -c feat/settlement-plan
git switch -c feat/property-analysis
git switch -c feat/ai-analysis
```

### 브랜치 이름 규칙

```text
feat/기능이름
```

* 영문 소문자를 사용합니다.
* 여러 단어는 하이픈(`-`)으로 구분합니다.
* 작업 내용을 파악할 수 있는 구체적인 이름을 사용합니다.
* 개인 이름이나 의미가 불분명한 이름은 사용하지 않습니다.

권장 예시:

```text
feat/signup
feat/settlement-plan
feat/property-analysis
feat/ai-analysis
feat/profile-readme
```

피해야 하는 예시:

```text
feat/test
feat/temp
feat/seokwon
feat/work
feat/new
```

## 3. 작업 흐름

```text
Issue 생성
    ↓
dev 브랜치 최신화
    ↓
feat/* 브랜치 생성
    ↓
기능 개발
    ↓
Commit 및 Push
    ↓
dev 대상 Pull Request 생성
    ↓
코드 리뷰 및 수정
    ↓
dev 병합
    ↓
통합 테스트
    ↓
안정화 후 main 병합
```

### 기본 작업 순서

1. 작업 내용을 확인하고 필요한 경우 GitHub Issue를 생성합니다.
2. 최신 `dev` 브랜치에서 `feat/*` 브랜치를 생성합니다.
3. 기능을 구현하고 정상 동작을 확인합니다.
4. 커밋 컨벤션에 맞춰 커밋합니다.
5. 원격 Repository에 브랜치를 Push합니다.
6. `dev` 브랜치를 대상으로 Pull Request를 생성합니다.
7. 코드 리뷰와 수정이 완료되면 병합합니다.

---

## 4. 커밋 컨벤션

### 커밋 메시지 형식

접두사는 영어로 작성하고, 작업 내용은 한글로 작성합니다.

```text
type: 작업 내용
```

예시:

```text
feat: 정착 계획 저장 기능 구현
fix: 매물 분석 실패 시 예외 처리 수정
docs: API 명세서 작성
refactor: 정착 비용 계산 로직 분리
```

### 커밋 타입

| 타입         | 설명                     |
| ---------- | ---------------------- |
| `feat`     | 새로운 기능 추가              |
| `fix`      | 버그 수정                  |
| `docs`     | 문서 전용 변경 사항            |
| `style`    | 코드 동작에 영향을 주지 않는 변경 사항 |
| `refactor` | 기능 변경 없는 코드 구조 개선      |
| `perf`     | 성능 개선                  |
| `test`     | 테스트 추가 또는 수정           |
| `build`    | 빌드 시스템 또는 의존성 변경       |
| `ci`       | CI 구성 변경               |
| `chore`    | 기타 설정 및 관리 작업          |
| `revert`   | 이전 변경 되돌리기             |

### 커밋 작성 규칙

* 하나의 커밋에는 하나의 작업 목적만 포함합니다.
* 커밋 메시지만 보고 변경 내용을 이해할 수 있도록 작성합니다.
* 커밋 메시지 제목은 한 줄(약 50자 이내)로 요약해서 작성합니다.
* 문장 끝에 마침표를 붙이지 않습니다.
* 불필요한 로그와 테스트용 코드를 제거한 후 커밋합니다.
* 동작하지 않는 코드를 `dev` 브랜치에 병합하지 않습니다.

피해야 하는 예시:

```text
수정
작업 완료
코드 변경
일단 커밋
fix: 수정
feat: 기능
```

## 5. Pull Request 규칙

기능 개발이 완료되면 `dev` 브랜치를 대상으로 Pull Request를 생성합니다.

```text
feat/* → dev
```

`main` 브랜치에는 기능 브랜치에서 직접 Pull Request를 생성하지 않습니다.

```text
feat/* → main  // 금지
```

### PR 제목

PR 제목은 커밋 메시지와 동일한 형식을 사용합니다.

```text
type: 작업 내용
```

예시:

```text
feat: 정착 계획 입력 기능 구현
fix: AI 분석 결과 저장 오류 수정
docs: 개발 공통 규칙 문서 추가
```

### PR 본문 양식

```md
## 작업 내용

- 이번 PR에서 구현하거나 변경한 내용을 작성합니다.

## 확인 방법

- 실행/테스트 절차와 확인한 케이스를 작성합니다.

## 관련 Issue

- Closes #이슈번호

## 화면

UI 변경이 있는 경우 스크린샷을 첨부합니다.

## 참고사항

리뷰어가 확인해야 할 내용이나 남은 작업을 작성합니다.
```

### PR 작성 전 확인사항

* [ ] 대상 브랜치가 `dev`인지 확인했습니다.
* [ ] 로컬에서 정상 동작을 확인했습니다.
* [ ] 최신 `dev`의 변경사항을 반영했습니다.
* [ ] 충돌 여부를 확인했습니다.
* [ ] 불필요한 파일과 로그를 제거했습니다.
* [ ] 관련 문서를 함께 수정했습니다.
* [ ] 환경변수와 개인정보가 포함되지 않았는지 확인했습니다.
* [ ] AI가 작성한 코드를 직접 이해하고 검토했습니다.

## 6. 코드 리뷰 규칙

* 작성자는 자신의 Pull Request를 직접 승인하지 않습니다.
* 최소 한 명 이상의 팀원이 변경사항을 확인한 후 병합합니다.
* 리뷰어는 코드의 의도와 동작을 확인합니다.
* 수정이 필요한 내용과 선택적인 제안을 구분합니다.
* 리뷰 의견에는 가능한 한 답변을 남깁니다.
* 리뷰 내용을 반영했다면 어떻게 반영했는지 코멘트로 남깁니다.

리뷰 의견은 다음과 같이 구분합니다.

```text
필수: 병합 전에 반드시 수정해야 하는 내용
제안: 더 나은 방법을 제안하는 내용
질문: 코드의 의도나 동작을 확인하는 내용
참고: 현재 수정하지 않아도 되는 참고사항
```

---

## 7. 병합 규칙

* 리뷰와 수정이 완료된 Pull Request만 병합합니다.
* 충돌이 있는 상태에서는 병합하지 않습니다.
* `main`과 `dev` 브랜치에 직접 Push하지 않습니다.
* `feat/*` 브랜치는 `dev`에 병합합니다.
* `dev`에서 통합 테스트를 완료한 후 `main`에 병합합니다.
* 병합이 끝난 `feat/*` 브랜치는 삭제합니다.

```text
feat/* → dev → main
```

## 8. 문서 관리

기능이나 설계가 변경되면 관련 문서도 함께 수정합니다.

| 변경 내용          | 함께 확인할 문서                 |
| -------------- | ------------------------- |
| API 요청·응답 변경   | API 명세서                   |
| 테이블·컬럼 변경      | ERD 및 테이블 명세              |
| 기능 흐름 변경       | 기능 명세서                    |
| 화면이나 사용자 흐름 변경 | 화면 설계서                    |
| 사용자 입력 조건 변경   | 요구사항 정의서                  |
| 개발 규칙 변경       | CONTRIBUTING.md 또는 코드 컨벤션 |

기능을 변경했다면 관련 문서도 같은 PR 또는 후속 작업에서 함께 업데이트했는지 확인합니다.

## 9. 보안 및 Repository 관리

다음 정보는 Git에 Commit하지 않습니다.

* 비밀번호
* API Key
* Access Token
* Refresh Token
* 데이터베이스 접속 정보
* 실제 환경변수 파일
* 개인정보가 포함된 테스트 데이터

환경별 설정값의 **키 구조만** 예제 파일로 공유합니다.

```text
.env.example
application.yaml.example
```

실제 설정 파일은 `.gitignore`에 추가합니다.

* `.env`
* 실제 운영·개발 비밀값이 포함된 설정 파일
* 인증서, 개인 키 등의 비밀 파일

Git에 이미 올라간 비밀값은 파일만 삭제해도 커밋 이력에 남으므로, 해당 키·토큰은 즉시 폐기하거나 재발급합니다.
