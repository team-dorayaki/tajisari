# 프론트엔드 개발 지침

## 기본 원칙

- React, TypeScript, Vite, Tailwind CSS, shadcn/ui를 사용한다.
- 기능 단위로 작업하고 한 이슈의 범위를 다른 기능으로 확장하지 않는다.
- 사용자가 화면을 직접 확인하고 승인하기 전에는 커밋하지 않는다.
- 브랜치 이름은 `feat/fe-{이슈번호}-{기능명}` 형식을 사용한다.
- 기능명은 영문 소문자 kebab-case로 작성한다.

## 레이아웃

- 모바일 퍼스트 방식으로 구현한다.
- 최상위 앱은 `width: 100%`, `max-width: 430px`, `min-height: 100dvh`로 구성한다.
- 넓은 화면에서는 앱을 중앙 정렬하고 외부에 중립색 배경을 표시한다.
- 내부 요소에 특정 기기 기준 고정 너비를 사용하지 않는다.
- 기본 좌우 여백은 16~24px 범위에서 디자인에 맞게 사용한다.
- 주요 배치에는 Flexbox 또는 Grid를 사용하고 절대 위치를 남용하지 않는다.
- 고정 하단 요소에는 `safe-area-inset-bottom`과 충분한 콘텐츠 여백을 적용한다.

## UI와 접근성

- 색상, 간격, 글꼴, 반경과 그림자는 디자인 토큰을 사용한다.
- 민트 계열 강조색을 직접 반복하지 않고 브랜드 토큰을 사용한다.
- 버튼과 입력 요소의 최소 터치 영역은 44px로 한다.
- 금액은 통화와 천 단위 구분을 일관되게 표시하고 숫자에는 tabular 숫자를 사용한다.
- 폼과 비동기 기능은 기본, 활성, 오류, 비활성, 로딩, 성공 상태를 고려한다.
- 반복이 확인된 요소만 공통 컴포넌트로 추출한다.

## 상태 관리

- 컴포넌트 내부 UI 상태는 React의 로컬 상태를 사용한다.
- 검증이 필요한 복합 폼의 입력값, 유효성, dirty 상태는 React Hook Form과 Zod로 관리한다.
- 화면 간 공유하거나 폼에서 적용한 저장 전 draft는 Zustand로 관리하고 기능 폴더 안에 배치한다.
- 계산 가능한 값은 중복 저장하지 않고 원본 상태에서 계산한다.
- 서버 상태는 실제 API 연동 시 TanStack Query로 분리한다.

## API 대응형 UI

- 서버 API와 연동될 예정인 UI는 목업 단계부터 예상 API 응답 형태로 구성한다.
- 목록의 렌더링, 검증, 계산은 항목명이나 배열 순서가 아닌 안정적인 ID, enum, metadata를 기준으로 처리한다.
- API DTO, 클라이언트 편집 상태, UI 표시 모델은 역할이 다르면 분리한다.
- 서버에 저장된 상태와 저장 전 편집 draft를 분리하고, 저장 시점에만 API 요청 데이터로 변환한다.
- 로딩, 성공, 오류, nullable, 빈 목록, 알 수 없는 상태를 처리할 수 있게 구성한다.
- 합계와 노출 여부 같은 파생 값은 필드명 하드코딩 없이 데이터의 타입과 metadata에서 계산한다.
- 통신 로직은 교체 가능한 비동기 API 함수나 모듈 경계 뒤에 둔다.
- API 계약이 불명확하면 구현 전에 사용할 필드와 상태에 대한 가정을 사용자에게 확인한다.
- 서버 연동 계획이 없는 정적 UI에는 불필요한 추상화를 추가하지 않는다.

## 검증

- UI 변경 후 320px, 375px, 430px와 데스크톱 중앙 배치를 확인한다.
- 가로 스크롤과 하단 고정 영역에 가려지는 콘텐츠가 없는지 확인한다.
- `npm run lint`와 `npm run build`를 실행한다.
- 브라우저 도구를 사용할 수 있으면 변경 화면의 스크린샷을 남긴다.
